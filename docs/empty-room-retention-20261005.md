# 建立聊天室即保留（2026-10-05）

## 使用者決定與驗收目標

按下建立並成功後，未改名、已改名、尚未送出訊息的聊天室均保留。工作區、模型、推理程度、權限、可選子代理設定及既有附件不因切換、閒置釋放或完整重啟而遺失。只有使用者明確封存／刪除才改變清單；不傳假訊息保存對話，不永久占用原生程序。

## 已重現根因

- K 在 `thread/start` 後寫下清單，但 Codex 尚無第一回合的原生對話可能只存在該 app-server 記憶體。
- 舊 `unsentSessions` 只保留在同一 controller；共用聊天室池切到第五個以上，會關閉較早且閒置的 controller。整個 K 重開亦會失去它。不是計時到期、改名導致或 Google 登入問題。
- 使用目前正式相同的 Codex **0.160.0**，全新假資料 CODEX_HOME、不搬登入、不送任何回合：一般 `thread/start`、成功 `thread/name/set`、`historyMode:paginated` 三種情況，在新 host 均無法讀回／resume 空白對話。回傳 path 不等於檔案已保存；不能靠改名或多讀一次解決。
- 切換失敗保留舊畫面是既有保護；錯誤顯示在 Opus 畫面不表示該 Opus 歷史也壞掉。

## 最小修正

- 主清單增加 Codex 的 `{nativeThreadId, hasSubmitted}`：聊天室 ID 維持不變，原生 ID 只在未提交過工作的空房間需要重新準備時更換。名稱、附件目錄、待送佇列與 UI 歸屬不換 ID。
- 原生連線仍依現有啟動／MCP 初始化流程準備；只在使用者實際送出時呼叫 `turn/start`。保留 active 加最近三間的既有資源釋放方式，不另建程序池。
- 空房間重開不讀不存在的原生歷史。已有送出／審查嘗試者仍讀回原生歷史；送出前先原子保存 `hasSubmitted:true`，即使回應不明也不改成空房間或自動重播。較舊的改名快照不能清掉這個標記。
- Opus 首查指出首次請求被明確拒絕也會留下提交標記，造成空房間無法重開。已補修：原本是空房間、收到原生錯誤回應且沒有已開始回合，才以內部明確選項還原未提交狀態；不自動重送，逾時／斷線仍保留不明狀態。一般 metadata 保存不能清掉已提交標記。
- Codex adapter 只映射協定的 thread identity 欄位，不遞迴改寫文字、工具內容或子代理 ID；核准、原生子代理父層讀回、停止、分支與 MCP readiness 沿用同一入口。
- Claude 已經持久保存零回合 projection。另修正對閒置 Claude 聊天室改名時，主清單應使用該聊天室的 effort／workerPolicy，不應拿目前房間的值。
- Gemini 已有零回合保存，不加另一套機制；補上未改名／改名後新 controller 重開與首次送出的回歸測試。Gemini 目前無可選子代理策略介面，不額外新增。
- 可恢復的新式空白 Codex 房間也可沿用既有工作區移動；歷史、權限、忙碌拒絕與原附件歸屬規則不變。

## 舊資料邊界

沒有新標記的既有清單不能單憑 `lastUsedModel:null`、名稱或錯誤內容推定從未送出。不得批量重建成空白。

使用者已明確確認的舊空白聊天室，僅於正式 K 停止後逐一核對其精確 ID、清單與原生缺少歷史的狀態，再補上未提交標記；不刪除原清單或搬移附件。尚未執行正式補記；其他已開始工作的聊天室不動。

### 程式退版相容性

舊版 K 不認得新增加的原生 ID 綁定。已在新版重新準備過的 Codex 空房間，若退到本修正之前的程式，清單及資料仍在，但舊程式可能無法開啟它；需回到含此修正的版本。這不是對話資料還原，不以程式退版承諾新式房間可由舊程式正常續接。
