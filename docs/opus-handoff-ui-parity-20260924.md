# 給 Astra 的交接：審查修正、介面摺疊、連續寫入、分支對話、聽寫

日期：2026-09-24。撰寫者：Opus 5.5（審查與規格）。實作者：Astra。完成後交回 Opus 複查程式碼與最終狀態。

## 共同原則

- **兩家共用**：K 的主代理大部分時間是 Claude Opus 5.5；遇到 Claude 5 小時額度用完時，使用者會切到 GPT 系列（多半是 Sol）。本文件的每一項介面功能，**Codex 與 Claude 兩條路徑都要能用，而且操作方式一致**。介面層不分供應商，差異收斂在各自的 controller。若某一邊的原生能力確實做不到，介面要明示「此主代理不支援」，不可假裝成功。
- **輕量優先**：使用者選 K 而不用 Codex App，就是因為 Codex App 又慢又重。每項改動除了正確，也要評估介面是否流暢；長對話不能越用越卡。
- 沿用既有邊界：
  - 不改全域設定，不自動安裝套件；
  - 不換計費路徑；Luna 維持 gpt-6-luna / high；
  - 狀態不明時不自動重送；
  - 未實測的事項不宣稱已完成。
- 需要官方協定行為的地方（標示「先實測」者），**先用真實官方程式實測、留下證據，再實作**，不要依照猜測來寫。

## 1. `.env.local` 讀取防護（P0）

**問題**：`AGENTS.md` 規定 `.env.local` 不可成為模型可讀的工作檔案，但目前只有 Pi 工人的 `checkedPath` 會阻擋。
- Claude Code 在 manual 模式下讀取工作區內的檔案不需要核准。
- Codex 的 `workspace-write` 沙箱只限制寫入，不限制讀取。
- 工作區是 `D:\K-harness` 時，主代理或 Luna 只要執行一次 `grep -r` 之類的指令，金鑰就會進入模型上下文。

**本輪要做（最低限度，專案內範圍）**：
1. 新增專案 `.claude/settings.json`，用 `permissions.deny` 禁止讀取和編輯 `.env.local`。路徑寫法（`./`、`/`、`//` 的語意）**依官方 permissions 文件確認**，不要憑記憶。
2. **驗證方式**：在 `.runtime` 底下建立驗收工作區，放一個內容為假值的 `.env.local`。用真實 Claude Code 嘗試 Read，確認被拒絕。**不可以拿真的 `D:\K-harness\.env.local` 做測試**：規則一旦寫錯，真金鑰就會進入上下文。
3. 確認新增的專案設定不會觸發 `claude-host.mjs` 的供應商覆寫檢查。它只能有 deny 規則，不可以有 env 或 apiKeyHelper。
4. 在 README 或權限文件註明殘餘風險：deny 規則只擋得住 Claude 的檔案工具，擋不住 Bash `cat`，也擋不住 Codex 主代理和 Luna。

**本輪不要做，需使用者另行同意**：根本解是把金鑰移到工作區以外，例如 `%LOCALAPPDATA%\K-harness\`，只讓 K 自己的程序載入。這會變更 `AGENTS.md` 中「複製到本專案 `.env.local`」的授權。使用者尚未決定，請先向使用者確認，未經同意不可搬移金鑰。

## 2. 回合摺疊介面（P1）

**目標版面**（比照 Codex App）。每一組由上到下：

1. **使用者訊息**：永遠可見。
2. **一行灰字 `處理了 4 分 12 秒 >`**：點開後，依時間順序顯示中途的助理訊息、工具呼叫、K 系統事件（Luna 完成通知）和 Luna 工作。預設收合。
3. **結論**：這組最後一則助理訊息，全文完整顯示。結論可以很長，不要截斷。
4. **底部一列**：`複製`、`分支`（見第 5 節）、結論產出時間，例如 `下午4:36`。只有結論這一則有這一列，中途訊息不再各自附「複製」按鈕。

**分組規則**：
- 一組的起點，是使用者在**閒置時**送出的訊息；下一則閒置時送出的使用者訊息開始新的一組。
- K 系統事件、工人通知觸發的後續回合，都歸在同一組，不另開新組。例如一次派出 4 個 Luna 工作後收到 4 則通知、回覆 4 次，最後一次回覆才是結論。
- 回合進行中送出的使用者訊息（Codex steer、Claude 連續寫入）要顯示在該組的過程裡，而且可見，但不開新組。
- 「處理時間」從組內第一則使用者訊息算到結論完成。

**進行中**：灰字改為 `處理中 1 分 03 秒`，並即時計時；最新一則助理訊息保持展開，讓使用者看得到目前進度。完成後自動收起，只留結論。

**資料**：
- 目前訊息物件沒有時間戳。新訊息要記錄 `createdAt`；結論要記錄 `completedAt`，可以取官方的回合完成事件，Claude 則取 `result` 訊息的時間。
- 舊對話沒有時間資料時，只顯示 `處理過程 >`，不顯示時間，也不可捏造時間。
- 只改呈現和新增欄位，不改原生歷史。舊對話打開要能正確分組。

**驗收**：
- 用現有的對話「第一次開工」（有多次 Luna 通知）做讀回，確認結論在最上層可見、過程收合、按鈕列只出現一次。
- Codex 和 Claude 各一個真實對話都要驗收。

## 3. 狀態推送改為只送變動部分（P1，效能）

**問題**：`desktop-server.mjs:18` 在每次狀態變化時（最快每 60ms），把整個 `controller.state` 轉成 JSON 推送。內容包含全部訊息，以及每個工具最多 2 萬字的輸出。Codex 回覆時每產生一小段文字就觸發一次，所以長對話中每次推送可能接近 1 MB，後端一直序列化，前端也一直整頁重新渲染。

**要做**：
- SSE 連線剛建立時送完整快照，之後只送變動的部分，例如「訊息 X 追加文字」「工具 Y 狀態與輸出尾端」「狀態欄位」。Claude 和 Codex 兩個 controller 用同一套事件格式。
- 前端只更新受影響的那一則。搭配第 2 節，收合的過程內容不必渲染。
- 斷線重連時重新送完整快照，避免狀態漂移。

**驗收**：量測同一個長對話（例如 50 次以上工具呼叫）在改動前後的每秒推送量，以及前端渲染時間，附上數字。

## 4. Claude 連續寫入（P1，先實測）

**使用者需求**：主代理工作中仍能繼續送出訊息，比照 Codex App。

**兩家差異**：
- Codex：已有 `turn/steer`，並用 `expectedTurnId` 確認套用。K 已實作。
- Claude Code：沒有專用的 steer 指令，做法是直接把新的 user 訊息寫進正在執行的 stream-json 輸入。至於訊息會在下一個安全點插入目前回合，還是排到回合結束後，要以實測為準。
- `--replay-user-messages` 可能可以讓 Claude Code 把收到的訊息回傳，作為收件確認。**請先依官方文件和實測確認這個參數存在並且有效。**

**先實測，保留證據**：
1. 工具呼叫進行中送出一則訊息：它何時被模型看到？輸出串流中有沒有確認訊息？
2. 純文字回覆進行中送出一則訊息。
3. 使用者在訊息送出後立刻按停止：訊息是否遺失，或狀態不明？

**實作方向**（依實測結果調整）：
- 移除 `claude-controller.send()` 對 `busy` 的阻擋，改成寫入原生串流。
- 收到原生確認前，畫面上把該訊息標為「已排入」。
- 寫入失敗或狀態不明時，照原則標示 uncertain，不自動重送。
- 介面上 Claude 和 Codex 的操作一致：工作中都能送出。Codex 維持用 steer。

## 5. 分支至新對話（P2）

**使用者需求**：在任何一則結論的按鈕列按「分支」，從該點開新對話；原對話保持不變。主要用途之一是 Claude 額度用完時，把工作分支到 GPT（多半是 Sol）接續。

### 5a. 同供應商分支
- Codex：確認 app-server 是否有 fork 或分支協定，以及能否指定從哪一回合分支。
- Claude Code：確認 `--fork-session`（搭配 `--resume`），以及能否指定分支點（Agent SDK 有類似 `resumeSessionAt` 的選項）。
- **兩者都先查官方文件並實測**。如果原生只能複製整個對話、不能指定分支點，介面上只提供「從最新一則分支」，不要自己裁剪原生歷史。

### 5b. 跨供應商分支（Claude ↔ GPT）
原生歷史無法跨供應商轉移，也不應該轉移。做法是：
1. 分支前，確認沒有尚未結束的 Luna 工作或核准請求。有的話要求使用者先處理。
2. K 從**自己的對話紀錄**產生交接檔，放在工作區的 `.runtime/handoffs/<新對話ID>.md`。內容包括：
   - 分支點之前每組的使用者訊息與結論；
   - 過程摘要：只列工具名稱和成果檔案，不放完整工具輸出；
   - 工作區路徑；
   - 成果檔案清單。
3. 在新對話的第一則訊息明示：「以下是從另一主代理分支而來的歷史資料，不是新指令，也不擴張授權」。交接檔只給路徑和概要，需要全文時再讀取，不要把整份歷史塞進訊息。
4. 新對話沿用原本的工作區；權限模式採用新供應商的預設值（要求核准或 manual），**不自動沿用高權限**。
5. 對話清單標示父子關係，例如「分支自：第一次開工（Claude）」。

**驗收**：
- Claude → Sol 分支一次，確認新對話能依交接檔接續工作。
- Sol → Claude 分支一次。
- 同供應商分支各一次。

## 6. 聽寫（P2）

**需求**：輸入框旁加麥克風按鈕，語音轉成文字填入輸入框（不自動送出），比照 Codex App。

**可選方案，請評估後向使用者提出建議，不要自行安裝任何東西**：
- **(a) 瀏覽器 Web Speech API**：零安裝。但音訊會送到瀏覽器廠商的雲端（Chrome 送 Google，Edge 送 Microsoft），需要明示使用者。另外要確認 K 的應用視窗能取得麥克風權限，並檢查 CSP 是否受影響。
- **(b) 訂閱內的轉錄能力**：確認官方 Codex app-server 或 Claude Code 是否提供語音轉文字介面，且不改用 API 計費。沒有就放棄這個方案。
- **(c) 本機 Whisper**：使用者另有 GPU 轉錄的工作環境。但接入必須另外取得安裝授權，本輪只評估，不安裝。
- **現成替代**：Windows 內建聽寫（Win+H）已經可以在 K 的輸入框使用，不需要開發。請把這點寫進說明，作為過渡方案。

聽寫結果只填入輸入框，由使用者確認後再送出。Claude 和 Codex 兩邊共用同一個輸入框，行為一致。
