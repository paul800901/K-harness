# 2026-10-06 主代理容量備援與 Gemini 依序交接

## 範圍與狀態

使用者要求全部修好：Luna 主代理遇到官方容量錯誤，以 GPT-6.1 Sol／中接手；聊天室原有模型／推理選單同步實際執行設定；查明並修正第五個 Gemini 帳號被跳過及手動切換誤報忙碌。

本批已完成候選修改、實測與真正 Opus 複查，準備固定版本後部署。使用者已明確回覆「我已離開並停止 K，可以套用」，唯讀確認正式服務與 K 自有核心程序已退出；不強制停止、恢復或重送既有工作。套用前南區程式為 `e794521`；東區不更新。較高階備援的具體順序尚未定案，本批只接 Luna → Sol／中，不自行增加下一級。

## 根因與修正

### 1. 容量錯誤不是額度耗盡

原生紀錄的主回合錯誤為 `server_overloaded`；安裝中的 Codex 0.160.0 產生的 app-server schema 將它對外表示為 `TurnError.codexErrorInfo = serverOverloaded`。並非 `usageLimitExceeded`。主代理失敗後，已派出的 Gemini 工人仍可能繼續，不能因主回合結束就重派。

- 只在目前 Luna **主回合原生確認 failed + serverOverloaded** 才執行一次同對話接續；不在 transient retry、一般網路錯誤、權限、登入、額度或子代理失敗時觸發。
- 重新讀取原生回合及官方可見模型清單，必須實際提供 `gpt-6.1-sol` 與 `medium`；缺少就回報，沒有另一條自動升級鏈。
- 新回合只帶 K 的接續／核對指示，不重送原始任務或附件。保留同一原生歷史、訂閱與原權限；不操作帳號、不停止或重派既有工人。AI 仍須查實際成果與工人狀態，只續做已授權的未完成工作。
- 原先 active、因錯誤變 blocked 的同一目標，在 Sol 覆寫成功後僅設定 `status: active`；不重新建立目標、不傳 objective/tokenBudget、不重設用量。目標已暫停、換掉、完成、預算／額度限制則不自動恢復。使用者停止／離開優先。
- 只收到原生啟動事件、但 RPC 回覆遺失時，依已知啟動證據保存實際模型，不再送一次；結果不明且無啟動證據則保留待確認。

依據：官方 [app-server 協定](https://learn.chatgpt.com/docs/app-server) 的 turn override 會沿用為後續同 thread 預設；goal status-only 更新保留原目標及用量。實際可用性另以下方原生假資料測試為準。

### 2. 看得到目前執行的型號／強度

- 沿用輸入框現有模型與推理選單，不新增管理面板。原生接受 Sol 後同步為 Sol／中，清掉先前 Luna 的推理草稿；執行中仍不可誤改，但文字保持可讀。
- 既有 `modelChanges` 加容量原因、來源回合與強度；重新開啟對話後仍有一則簡短交接紀錄。
- 接續指示不顯示成使用者長訊息；只把該回合第一則系統接續投影為 note，同回合後續真正插隊訊息仍顯示。一般手動換模型與訊息引用邊界不變。

### 3. 第五個 Gemini 帳號被跳過

只讀追查確認：保存清單有五個帳號，沒有寫死四個。第四個額度耗盡後，主代理明確指定第一個，之後又指定第二個；原 `acquire` 只有省略 accountId 時才走依序選擇，因此繞過第五個。第五個卡片的 100% 是新增時的舊查詢，不足以證明目前可用或登入有問題。

- worker acquire 不再讓 accountId 繞過順序：目前未確認耗盡就留在目前帳號；確認耗盡且全部 Gemini 工作已結束，從目前的下一個保存位置往後循環（第四 → 第五 → 第一）。
- 每個候選都重新確認原生登入及額度；未知、過期、沒有可用官方窗口不當成有額度。新鮮官方耗盡才繼續查下一個。不因一般錯誤換帳號，不跨帳號並行，不重播工作。
- 真正需要交接既有工作時，仍由主代理先核對已停止工人的成果，以新 requestId / handoffFrom 只接剩餘部分。
- 全部帳號官方確認耗盡後，主代理才可依使用者已明確授權的備援模型處理剩餘工作；不是 K 擅自把每一項 Gemini 失敗改派 Luna。
- 本人在設定頁手動切換仍可選指定帳號，不受 worker 的順序限制。

### 4. 手動切換誤報忙碌

背景額度查詢與登入／切換共用 exclusive 狀態，但人工 activate 原本不像 acquire 會等待 refreshPending。假依賴測試重現：只有額度查詢尚未回來時，按切換就被當成工作／登入中。現在先等該查詢結束，再核對真正工作、登入與不確定狀態；不是強制解鎖。截圖那一次點擊未有逐請求歷程，不能宣稱所有忙碌提示都由此造成。
