## 真正 Opus 複查與採納

官方 Claude Code 2.1.294、既有 K Claude.ai 訂閱，實際 assistant model `claude-opus-5-5`；不是代理更名或其他模型模擬。原封包、原生 events、identity、完成收據及原文保存在 `D:\K-harness\.runtime\quota-discussion-20261008\code-{review,recheck,final,acceptance}*`。

1. 初查指出恢復批次 throw 後 UI 可能重送、整理顏色需優先中性、耗盡提示不能對失敗資料承諾全組恢復、剛全查後選中工人又重查。採納：記錄一次嘗試、避免 usage 退回單查重送、成功全組證據才承諾恢復，選中候選重用 60 秒內的剛成功恢復結果；正常工人使用前仍實查。
2. 補查指出只比較 deadline 會在延後到多個 reset 都過期時 key 漂移，造成多次批次。採納最小修正：唯一記憶體欄位改記嘗試時間；同次嘗試前已到期的其他窗口不得另起批次。新增五個不同期限全過期、原帳號更新後切換 throw、三次 usage 不重查及人工全查仍可用的測試。acquire 不吞恢復失敗，不讓不明工作續跑。
3. 第三輪指出 usage gate 不能永久擋掉正常單帳號到期查詢。採納：原有 60 秒節流後允許單帳號查詢，但整組同次失敗批次不自動重播；新 reset 到期只查目前 A、沒有 activate，回歸通過。因 UI 原有 10 秒刷新，針對實際 `login.status` throw 的缺口記錄既有 lastQueryAt 與 stale、不改先前成功登入，save 後仍 throw，不假成功或讓 acquire 續跑；60 秒內不重查，過後正常重查。
4. Opus 要求確認三家 controller 失敗不會由新 helper 繞過節流。實際 catch 都標 stale；三家各補 reset 到期失敗、連續 usage 只查一次、301 秒後可查的測試通過。最後驗收複查結果見後續讀回。
5. 第四輪確認前述 P2 修正，另指出各列個別過去的零不能湊成同時全組零。採納：以最後成功觀察時間作為共同判斷點，任一帳號在這個時間已重設就不是全組耗盡恢復。新增 A 到 E 依序零但 A 在 E 觀察前早已到期，UI 不查整組、工人只查到期 A 的回歸，78/78 通過。延後已有真同時零證據的全組恢復仍保留。
