# 聊天室並行工作與切換修正

## 結論與生效範圍

使用者要求：A 聊天室的主代理工作時，可以切換到 B 繼續討論；不是停止 A 才能看 B。

## 原因與做法

- 前端原本把目前主代理的 busy 當成側欄、新對話的停用條件。
- 後端不只是按鈕問題：單一 Unified controller 只持有一個作用中對話與輸入佇列。切換時會重新開啟同一控制器、或關閉舊供應商連線。因此不能只移除畫面上的 disabled。
- 新增對話層的 controller pool：每個已開啟的聊天室持有自己的 Unified controller、原生 host、佇列及回呼；畫面選擇只是改變顯示哪一份狀態。沒有重寫原生執行、歷史或權限核心。
- 單一原生 controller 的「忙碌時不能改換它所屬的對話」檢查保留。舊的 busy-switch 測試仍應通過；並行由外層獨立的 controller 達成。
- 同供應商、跨供應商均可各自保留工作；新對話直接指定工作區，不先改動正在執行中的聊天室。
- 已在記憶體中的正常聊天室切回時不重開原生連線。閒置的故障連線仍可重連，包括既有的子代理連線失敗與瀏覽器取消恢復；不重送歷史指令。

## 不互相影響的邊界

- 送出、待送佇列、停止、核准、主模型、壓縮、檔案搜尋、審查、附件與成果讀取，均帶入操作來源的 threadId。缺少或不是已開啟對話的 ID 會拒絕，不默認操作目前畫面。
- A 的串流、核准與完成事件留在 A；B 畫面不顯示 A 的訊息或核准內容。側欄只顯示「處理中／需要確認」。
- 停止 B 只暫停 B 佇列及停止 B。A 的主工作、待送佇列及子代理保留。
- 草稿、待送附件依聊天室保存。附件上傳晚到仍回到原聊天室；切換時不清除附件。
- 成果預覽晚到時若已切換對話，不把舊結果塞到新的畫面。
- 分支要求來源為目前顯示且已結束的對話，依原生規則建立；外層同步新的 ID，其他背景聊天室不受影響。
- 刪除封存紀錄前先確認目標沒有背景工作、待核准、待送訊息或未結束子代理；不以切走畫面代表工作已停。
- 停止整個後端時，先等待已接受的開啟操作完成，再關閉所有持有的控制器，避免新 host 在關閉後才出現。

## 修正中找到的晚到回覆問題

介面解除切換限制後，另驗出「A 送出中切去 B，A 送出失敗，回 A 草稿消失」。原因是 A 的輸入元件已卸載，只還原舊元件不足以保存草稿。

已改為按 A 的 ID 保存失敗草稿；成功回覆只清除那次送出的草稿與附件，不清掉回到 A 後另外輸入的新稿。這是本次並行切換直接引出的問題，未更換輸入元件或更改既有 IME 修法。
