## 一、原始阻擋：測試提早關閉正在進行的交接

- `test/fresh-target-model.test.mjs` 最多等 2500ms，每 10ms 讀取交接收據。產品持久化的單次 Windows 換名鎖等待就允許 10 秒，還有同步落盤與多次序列寫入，因此測試期限不是產品成功條件。
- 原失敗留下的檔案顯示：測試在新聊天室建立期間逾時，`finally` 呼叫控制器關閉；關閉使來源檢查拒絕送出，最後記成 `uncertain`，新聊天室沒有收到交接。這是測試收尾造成，不是原本的交接失敗原因。
- 仍無法由原有檔案確定那次約 2.6 秒耗在同步落盤、Windows 檔案鎖或系統排程；不宣稱已證明 Defender 或 CPU 是原因。正式環境不使用 Sandboxie，候選目錄名稱只是歷史遺留。
- 修正僅在該測試：先訂閱既有控制器 `onChange`，再送完成事件；事件到達才讀正式收據，不固定頻率輪詢。30 秒看門狗只防測試掛住，會帶最後狀態與經過時間，不把逾時當成功。
- 新增 2800ms 受控開啟延遲：舊等待方法確實失敗，新方法確認 `sent`、正確模型與推理程度、只建立及交接一次。
- 新增閘門控制的「建立期間關閉」用例：重現原收據的 `uncertain`、新聊天室 ID、相同錯誤與未送出交接，證明收尾因果。

## 二、完整測試另外抓到的真實漏通知問題

- 首次完整套卡在既有 `test/codex-flash.test.mjs` 的 native goal / worker notification race；沒有把這次卡住算通過。
- 送出工人通知被原生明確拒絕時，結果會放回佇列並保存。若原生下一回合的完成事件在該通知收尾前到達，事件處理因通知仍忙而返回；原 `finally` 只會接續成功送出的分支，拒絕後的唯一完成事件因此遺失。
- 已用受控閘門重現：完成事件先於拒絕收尾，等完成事件處理確實返回，再放行拒絕。舊產品在有界等待內失敗 `native completion wakeup was lost`，新產品通過。
- `src/desktop-controller.mjs` 增加本次執行期的原生終態序號，只記目前擁有回合且通過 ID 過濾的終態，不把外來或重複通知當新完成。拒絕收尾時保留已到達的原生失敗狀態，不覆蓋成完成；Gemini 就緒交接也不再留下已過時的等待旗標。
- 只有明確協定拒絕、期間有新原生終態、同一 host／對話／意圖且目前真正 completed 的既有佇列才再檢查。沒有新完成、失敗、停止與傳輸結果不明均不因此重送。沒有新增排程器、持久狀態、帳號切換或使用者設定。
