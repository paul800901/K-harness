## 建議採取的最小方案（待實作，不是已完成能力）

### 1. 操作指令有生命週期，不拿歷史當現在

暫停請求在完成或被本人後續指令取消前有效；明確繼續後，之前那次更新 K／暫停不應再次生效。等待工人收尾的 pending pause 仍合法。永久更正、工作授權、一次性操作分開；舊交接檔恢復後只是歷史，不能單獨決定當下狀態。

不以簡單關鍵字／新自然語言分類器判斷所有訊息，也不把任何 native active 通知當作本人已取消待收尾暫停。原生 usage_limited／budget_limited、真正 blocked、failed 照原生語意處理，不能一律改 blocked，更不能用 paused 假稱本人要求。

### 2. K 提供現況，專案既有進度保留工作記憶

考慮沿既有 gateway 增加一個唯讀現況工具：原生 goal、本人訊息 id／順序、已確認恢復的來源、工人及原生壓縮資訊。只回傳本對話必要資料，不另建記憶資料庫。模型在派工／暫停等決策前按需讀回，而不是憑壓縮記憶猜現在。

中間狀態沿用**既有唯一進度／術語／事件／裁定檔**：最新更正的來源與被取代決定、已驗收範圍、在途工單 id、未決疑點與下一步。缺少欄位才補最小段落，不再抄一份所有狀態或另造 ledger。這些檔案也可能過期／被誤寫，須看来源和實際成果，不能把檔案存在當成正確。

Opus提議筆記結構checker及無引用警報；Astra不將它們整套列為第一批必要條件。訊息存在不代表語意正確、一般回覆未帶id不一定是未授權；應先確認可以取得可靠控制來源並以既有資料核對，避免新checker、誤報與提示噪音。即使做偵測，也不自動恢復、重派或改模式。

### 3. 真正驗證壓縮後如何重錨

現況提示必須涵蓋**原生自行壓縮與目標續行**，不能只在使用者發訊息／open/resume時刷新。先用新建假資料對話驗證本機0.161.0的公開協定／擴充：非使用者角色的提示／唯讀讀回入口是否支援、注入時機與模型可見性、有無打斷進行中工具、壓縮後是否仍有用。不修改正在翻譯的四個對話來試。

[官方 App Server 文件](https://learn.chatgpt.com/docs/app-server)列有原生壓縮事件、`thread/inject_items` 及 fork 的歷史複製語意。**文件存在不代表本台可用或本情境安全**；本輪未呼叫這些變更協定。rollout metadata／保留清單不是當次完整模型請求的證明，無法讀到的部分須保留 UNKNOWN。

### 4. 新脈絡交接是後備，不按壓縮次數自動重置

若上述機制實測後同類偏移仍反覆，或同對話持續壓縮失敗無法工作，再於安全批次邊界考慮新原生 session。用當前原始決定＋已驗收成果＋進度交接，不再把舊壓縮摘要壓一次搬過去。普通 fork 複製歷史不是清除偏移。

換session要明確處理同一可見聊天室、目標用量／狀態、工人歸屬、未知結果及本人授權；不能偷偷换 provider／model／effort／permissions，不能複製副作用或恢復已暫停目標。現在沒有足夠證據設「每N次自動換房」門檻，也不宣稱新session可消除全部翻譯錯誤。
