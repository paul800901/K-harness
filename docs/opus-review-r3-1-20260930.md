## 需修：取消「已開著聊天室的重新連線」後，聊天室停在假的「已連線」

**重現**（`.runtime/audit-20260929/r3-cancel-existing-room-probe.mjs`，假 host，直接載入正式 runtime 的 claude-controller，與 d7b58ef 逐位元相同）：

| 步驟 | 結果 |
|---|---|
| 開啟 Claude 聊天室 | ready |
| 改權限觸發重新連線，連線中按取消 | stop 回 `{cancelled:true}`，open 以「已取消連線」結束 |
| 取消後 | **status=ready、error=null**，但原連線已在重連前關閉 |
| 送出訊息 | 失敗：「請先開啟 Claude 對話，或等待目前工作結束。」 |

**原因**：claude-controller `open()` 會先關掉舊 host，再建立新 host；被取消時卻用 `Object.assign(state, previousState)` 把狀態整個還原成開啟前的 ready。conversation-controller 只會對 offline／error／uncertain 的聊天室自動重連，所以這個 ready 聊天室既送不出訊息，點回去也不會重連，只能靠再改一次權限或重啟 K 脫困。

Codex 端屬同一類問題，但只在「瀏覽器需恢復時先關舊 host」這條少見路徑發生。另外 Codex 在一般的重新設定路徑被取消時，內部的 items／uiTiming 已被重設，不會跟著 state 還原，屬輕微不一致。

**建議修法（小）**：取消時若這次 open 已關掉原本的 host，就不要還原成 ready：
- Claude 設成 `interrupted`：既有的 `send()` 遇到 interrupted 會自動重連。
- Codex 設成 `offline`：下次點開聊天室會自動恢復。

補一個測試：既有聊天室重連中取消 → 下一次送出（Claude）或下一次開啟（Codex）能正常恢復。

**修好前的暫時解法**：聊天室顯示正常但送不出訊息時，隨便改一次它的權限或推理程度就會重新連線；或重開 K。
