# 下載紀錄備份：去重與新批次保留上限

日期：2026-09-25。對應 Opus 複查 `opus-review-browser-live-view-20260925.md` 第九節。

狀態：已實作、假資料單元測試與實際 Edge／Chromium／MCP 驗證通過；**未啟用正式瀏覽器、未重啟正式後端、沒有清理既有 profile，也沒有登入真實帳號。**

## 這輪解決什麼

前一版每次啟動都複製三張下載表，原生恢復的舊列會再產生一批重複備份。本輪保留原有「瀏覽器未使用 profile 才處理、離線交易、下載相容性修正不動 cookie／其他歷史」邊界，補上：

1. **完整紀錄去重**：以一個下載 ID 的父列、全部網址鏈及分段列為一組，比對 schema 和所有欄位；孤兒子列也按 ID 分組。父列、網址鏈、分段或重複子列數量有變，就保存整組的新版本；相同資料只是資料庫列順序不同，不新增備份。不是只看 ID 或 GUID，所以不會漏掉重用 ID／同 GUID 的變更。
2. **新批次最多 5 批**：只在出現尚未備份的完整紀錄時建立一批，按交易內產生的遞增序號保留最新 5 批。淘汰時三張備份表與批次登記一起處理，不留半批。淘汰的是備份資料，不是已下載的檔案，也不是 cookie、localStorage、IndexedDB、瀏覽網址或訪問紀錄。
3. **不重建已淘汰的相同原文**：`k_download_history_seen` 只記錄完整組資料的 SHA-256 摘要，避免第 6 批淘汰第 1 批後，第 1 批相同舊資料再出現，又把已淘汰的網址重新存回備份。它不是另一份網址／檔名清單。
4. **維持原子性**：建立新備份、記錄摘要、清理原生三表與淘汰受管理批次，都在原有 `BEGIN EXCLUSIVE` 交易內。任何一步失敗便一起 rollback，沒有先丟掉舊資料再補救。

`archivedCount`／`archivedRows` 現在代表本次**新保存**的列數；完全重複時為 0，`backupBatchId` 為 null，但相容性處理仍會清空原生三表。呼叫端目前不依賴這些回傳計數。

## 明確限制：不能把保留上限說成隱私刪除

- **5 批只約束新版登記管理的批次。** 舊版 UUID 批次沒有可信建立時間；不把隨機 UUID 或 SQLite 內部表順序當時間猜測，也不自動刪除它們。第一次處理時只讀取它們建立去重摘要。若 profile 原本有 6 批舊備份，之後可能仍是「6 批舊備份 + 最多 5 批新備份」，不是總數已降至 5。本輪沒有對既有 profile 執行任何這類遷移或清理。
- **清除瀏覽器原生下載紀錄，不會自動清除 K 備份。** 原生表為空也可能只是 K 上次相容性處理的結果，不能據此猜測使用者按了清除。因此清除動作與 K 備份的同步刪除仍未接入，這部分的隱私問題不能標成已解決。
- 5 批是數量，不是 30 天：如果一直沒有新紀錄，保留中的備份不會隨時間自動到期。備份仍有原始網址，可能含 URL token。
- `seen` 每種不同版本保存一筆摘要，筆數仍會隨獨特版本增加；不是整份 History 的大小上限，也不是安全隔離或匿名化。此小量持久狀態的直接用途是防止過期原文反覆恢復。沒有建立另一套一般性封存服務。
- SQLite `DROP TABLE` 是邏輯淘汰，**不是鑑識級抹除**，未做 VACUUM／secure erase，也沒有承諾資料庫檔案立刻縮小或所有磁碟頁都不再含舊位元組。
- 可還原範圍現在限於仍保留的新版批次及未動的舊版批次；已淘汰新版批次不能從摘要還原。這是保留上限的明確代價。
- 登入資料與模型 shell 的作業系統隔離仍未完成。維持正式關閉、禁止真實帳號登入；這輪沒有修改 Windows 帳號、ACL、計費或既有瀏覽器設定。

後續若要提供人類的「清除下載紀錄」功能，須在明確清除操作下協調原生紀錄、K 備份及相關索引；不能以本輪 5 批上限代替。既有舊備份的清理須另外確認範圍與可還原性，不在本輪偷偷執行。
