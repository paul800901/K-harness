# 多模型討論：三種模式與 AI 調度需求定案（2026-10-08）

## 狀態與範圍

**本輪完成需求定案與文件記錄，沒有實作產品功能。** 未修改產品程式、原生核心、登入、模型設定或正式啟動指標；未安裝、部署、重啟、push 或操作其他聊天室的工作。使用者認可需求與調度原則，不等於已批准全部 UI 細節、資料結構、工程方案或正式部署。

本文件為這項新功能的目前需求來源。前面的 Astra／Opus 建議屬討論材料，未獲使用者確認的細節不得視為定案。

## 使用者已確認的需求

1. **三種模式並存，而非三選一或固定流水線。** 平行比較、交叉審查、多人討論各有適用用途；可以只使用其中一種，也可依同一件事的需要接續使用。
2. **兩種入口都要有。** 已與單一模型討論的聊天室中，可以直接發起多模型模式，不必重新交代整件事；也可以在一開始就選模式，不必先有單模型對話或等到不滿意才使用。
3. **背景由 AI 整理。** 帶入真正需求、必要事實、限制、原文／證據、使用者修正與仍不滿意的地方，不只轉述原模型自己的結論；人可以查看、修正，但不需要自己整理交接封包。
4. **AI 負責調度，不要求人逐輪操作。** 人交代議題、參與需求與限制後，AI 在該任務內安排誰回答、哪些分歧需要回應、何時查證、何時整理及停止。人不必逐輪按繼續、指定發言順序或管理底層 session。
5. **保留分歧，不硬湊共識。** 交付應區分共識、不同意見及其理由／證據、尚未確認的事與需要本人決定的取捨。達成一致不是完成的必要條件。

## 三種模式不可混同的語意

- **平行比較**：讓參與者針對相同需求與資料提出各自看法。若要真正獨立意見，就不能先給其他模型的本題結論；只做到本輪互不可見，不等於未受先前討論影響。
- **交叉審查**：明確指出被審查的內容／方案，讓模型提出問題、盲點與不同判斷；不是無目標地重讀全部聊天。
- **多人討論**：模型能回應彼此的論點，人能插話、追問或指定發言者；不是只有平行答案或子代理交回摘要。

## AI 調度的產品原則

- 不把「每輪都由人按繼續」設為必需流程，也不把「首輪＋一次互評＋整理」寫成所有任務的硬性輪數。先前固定小流程只是討論候選；本輪使用者確認的是由 AI 按任務調度。
- 不強制全部參與者每輪都重複發言。針對必要觀點、證據或未解決的分歧推進，已足以回答需求時整理並停止；沒有新增實質內容時不為湊輪數繼續。
- 人保留隨時補充、指定一位或全體、調整議題與停止的入口，不需要成為工程調度員。
- AI 調度不擴張資料／工具授權，不自動換指定模型、供應商、帳號或計費路徑，不把未知結果自動重播。討論成果不自動取得實作、寫入或部署授權。
- 模型之間的意見只是判斷材料，不是本人批准、外部事實驗證或工具操作授權。

## 尚未定案或未驗證的工程事項

- 共用既有聊天介面是 Astra 與真 Opus 的共同建議；現有房間內階段呈現、關聯討論房與具體畫面如何安排，仍需設計。使用者確認「從現有聊天室發起」不等於已經確認一定另開房或某個 backend 類型。
- K 直接協調三家原生對話是候選路線，不必預設依賴 GPT→Claude 工人派遣；需核對現有入口、權限、模型目錄及結果機制，不能把候選當已接通。
- 各核心原生歷史／壓縮仍由各自核心管理；共用討論紀錄不得假裝成供應商共同原生歷史。需要新上下文時由工程安排，不要求人管理 native session。
- 附件與公開資料查證按任務授權使用；實際跨核心讀寫邊界、並行能力、插話歸屬、整組停止、失敗與不明結果處理均需相稱驗證，不靠提示詞宣稱已強制保證。
- 不預先添加角色市場、工作流編輯器、投票分數、能力排名、共享知識核心、永久主持人或新管理頁。具體新增機制必須對應本功能的實際必要條件。
- 時間、訂閱用量與長討論的結果品質尚未比較實測，不承諾節省或固定倍數。
